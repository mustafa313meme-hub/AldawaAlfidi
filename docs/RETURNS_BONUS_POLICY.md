# سياسة المردود والبونص — `bonus_return_policy = Proportional`

**الحالة:** معتمدة من المالك. **الإعداد:** `Settings.bonus_return_policy = 'Proportional'` (القيم الأخرى Independent / FullBonusOnReturn تبقى مدعومة برمجياً لكن غير مفعّلة).

## 1. المبادئ
1. الكمية المباعة والبونص كميتان منفصلتان في كل سطر فاتورة، والبونص ليس خصماً مالياً.
2. أي مردود يمر عبر معاملة DB واحدة (Transaction) تنشئ معاً: `Return` + `ReturnItems` + `StockMovements` + `LedgerEntries` + `AuditLog`.
3. لا يُسمح بإرجاع كمية مباعة أو بونص أكبر من القابل للإرجاع.
4. لا Hard Delete: التراجع عن مردود يتم بقيد عكسي (Reverse).

## 2. الحقول المطلوبة في `InvoiceItems`
| الحقل | المعنى |
|---|---|
| `quantity` | الكمية المباعة الأصلية |
| `bonus_quantity` | البونص الممنوح أصلاً |
| `returned_quantity` | المباع المرتجع تراكمياً |
| `bonus_returned_quantity` | البونص المرتجع تراكمياً |
| `bonus_rule_id` | القاعدة التي ولّدت البونص (للإعادة الحساب) |
| `net_amount` | صافي المبلغ بعد الخصم (للحساب النسبي) |

## 3. القابل للإرجاع
```
sold_returnable  = quantity - returned_quantity
bonus_returnable = bonus_quantity - bonus_returned_quantity
```

## 4. الحالة A: إرجاع كمية مباعة (Proportional)
1. `remaining_sold = quantity - (returned_quantity + qty_now)`.
2. إعادة تقييم القاعدة على المتبقي:
   `entitled_bonus = floor(remaining_sold / rule.min_quantity) * rule.bonus_quantity`
   (إذا وُجدت عدة شرائح تُطبَّق الأعلى المستحقة، وبحسب القاعدة التي كانت سارية بتاريخ الفاتورة وليس اليوم).
3. `excess_bonus = (bonus_quantity - bonus_returned_quantity) - entitled_bonus` (إن كانت سالبة تصبح 0).
4. مبلغ الائتمان للكمية المباعة المرتجعة:
   `credit = qty_now × (net_amount / quantity)` أي بعد احتساب حصة الخصم.
5. البونص الزائد `excess_bonus` يُضاف تلقائياً إلى المردود كسطر `Bonus` إلزامي.

**مثال:** فاتورة 10 مباع + 2 بونص (قاعدة كل 10 + 2) بسعر 10,000.
- إرجاع 2 مباع ← المتبقي 8 ← المستحق 0 ← الزائد 2 ← يُرجَع البونص كاملاً (2).
- الائتمان = 2 × 10,000 = 20,000 (+ حركة مخزون للبونص بقيمة 0).

## 5. الحالة B: إرجاع بونص مستقل
- يسمح به المستخدم بصلاحية `returns.create` دون المساس بالكمية المباعة.
- الشرط: `qty ≤ bonus_returnable`.
- الأثر المالي: **صفر** (ليس خصماً نقدياً)، لكن يسجَّل قيد Ledger بمبلغ 0 للتتبع.
- الأثر المخزني: `ReturnIn` بعلامة `is_bonus = true` إذا كانت الحالة صالحة.

## 6. البونص الزائد غير القابل للإرجاع (تالف / مستهلك / منتهٍ)
افتراض مبدئي **يحتاج تأكيدك**: يتطلب موافقة (`returns.approve`) ثم يُنشأ قيد مدين (Adjustment) على العميل بقيمة `excess × unit_price`، ويسجَّل في Audit Log بسبب إلزامي.

## 7. حالة الأصناف المرتجعة
`condition ∈ {Valid, Damaged, Expired}`:
- Valid ← `ReturnIn` يعيد الكمية للمخزن/التشغيلة.
- Damaged/Expired ← حركة `Damage` / `Expired` ولا تعود للمخزون القابل للبيع.

## 8. حماية التزامن
- `SELECT … FOR UPDATE` على `InvoiceItems` المعنية داخل المعاملة.
- `Idempotency-Key` إلزامي على إنشاء المردود (مهم للمزامنة Offline).
- تحقق ثانٍ في قاعدة البيانات: `CHECK (returned_quantity <= quantity)` و`CHECK (bonus_returned_quantity <= bonus_quantity)`.

## 9. ما يُسجَّل لكل مردود
| الجهة | السجل |
|---|---|
| المخزون | `StockMovements` (ReturnIn / Damage / Expired) لكل سطر، مع batch وexpiry |
| الحساب | `LedgerEntries` نوع Return (دائن) أو Adjustment، وتحديث رصيد العميل |
| التدقيق | `AuditLogs` بالقيم القديمة/الجديدة وuser/device/IP |
| الفاتورة | تحديث `returned_quantity` و`bonus_returned_quantity` و`remaining_amount` |

## 10. حالات اختبار إلزامية
1. إرجاع مباع يُسقط البونص عن الشريحة ← بونص زائد إلزامي.
2. إرجاع مباع لا يُسقط الشريحة (مثلاً 20 + 5 ثم إرجاع 3) ← لا بونص زائد.
3. إرجاع بونص مستقل ثم محاولة تجاوزه ← رفض.
4. إرجاع أكثر من المباع ← رفض.
5. مردودان متزامنان لنفس السطر ← أحدهما يُرفض.
6. مردود مع خصم نسبي ← ائتمان مطابق لصافي السطر.
7. إعادة إرسال نفس الطلب (Idempotency) ← لا تكرار.
8. مردود تالف ← لا يرجع للمخزون القابل للبيع.

## 11. ملاحظات التنفيذ (Phase 4) — ما طُبِّق فعلاً في الكود
- **الحساب:** `src/sales/return-policy.ts` (`planReturnLine`) و`bonus.ts` (`bonusFor`) و`money.ts` (`creditForReturn`)، وكلها دوال نقية مغطّاة باختبارات (28 اختباراً).
- **البونص المستحق بعد المردود:** `bonusFor(remainingSold, rules)`؛ مع قاعدة واحدة (كل 10 + 2) يساوي `floor(remaining/min) × bonus`. مع عدة قواعد يختار **أفضل توليفة للعميل** (كل 20+5 وكل 10+2 ⇒ 30 وحدة = 7 بونص)، وهذا يضمن أن البونص لا ينقص أبداً بزيادة الكمية.
- **القواعد المعتمدة هي قواعد يوم الفاتورة:** كل سطر فاتورة يحمل نسخة (`bonusRuleSnapshot`) من القواعد التي بيع بها؛ تعديل القواعد لاحقاً لا يغيّر حساب المردود.
- **البونص الزائد المطلوب إرجاعه** يُضاف تلقائياً للمردود (`ReturnItem.required = true`). إن طلب المستخدم `billExcessBonus` (صلاحية `returns.approve`) يُحاسَب العميل بدلاً من الإرجاع بـ `الكمية × سعر الوحدة` (قبل الخصم) كقيد مدين `Adjustment`، ولا يجوز أن تتجاوز قيمته قيمة المردود (`BILLED_EXCEEDS_CREDIT`). البونص المحاسَب عليه يُحتسب «منتهياً» حتى لا يُطلَب مرة ثانية.
- **قيمة المردود:** `قيمة السطر بعد الخصم والضريبة × الكمية المرتجعة ÷ الكمية المباعة`، بتقريب تراكمي (telescoping) فمجموع المردودات الجزئية يساوي قيمة السطر تماماً بلا دينار زائد أو ناقص. مثال SRS: 10 × 10,000 خصم 10% ⇒ إرجاع 2 = **18,000** (وليس 20,000).
- **البونص المرتجع بالكامل مستقل:** `soldQuantity = 0` و`bonusQuantity > 0` ⇒ بلا أثر مالي (قيد Ledger بصفر) وحركة مخزون `ReturnIn` بعلامة `isBonus`.
- **التالف/المنتهي:** تُسجَّل `ReturnIn` ثم `Damage`/`Expired` في نفس المعاملة، فلا يدخل المخزون القابل للبيع ويبقى الأثر موثّقاً.
- **الحماية:** قفل `FOR UPDATE` على الفاتورة والعميل وسطور الفاتورة، وتحديث مشروط بالقيم المقروءة، وقيود DB (`returnedQuantity <= quantity` و`bonusReturnedQuantity <= bonusQuantity`)، ومفتاح `x-device-id + localId` ضد التكرار.
- **السياسات الأخرى:** `Independent` (البونص لا يتأثر)، و`FullBonusOnReturn` (أي مردود مباع يسترجع كل البونص المتبقي). تُقرأ من الإعداد `bonus_return_policy` عند كل مردود.
